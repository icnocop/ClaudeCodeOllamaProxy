# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local HTTP server that exposes the **Ollama API** and drives the local **Claude Code CLI** (via the `AJGit.Claude.AgentSdk` NuGet package), so Visual Studio 2022 17.14+ / 2026 / VS Code GitHub Copilot Chat's Bring Your Own Model **Ollama provider** can use Claude Code — including Copilot's native in-chat diff/accept-reject UI. It launches the `claude` CLI and nothing else (no cloud provider forwarding). See `README.md` for end-user setup.

## Git policy

**Never commit or push.** Do not run `git commit`, `git push`, `git tag`, or anything that writes to the repository or the git server — commits and pushes to the git server are done **manually by the user**. Read-only git commands (`git status`, `git diff`, `git log`) are fine. Make and leave changes in the working tree for the user to review and commit themselves.

## Commands

The solution (`ClaudeCodeOllamaProxy.slnx`) has **three projects**: `ClaudeCodeOllamaProxy.Core` (class library — all proxy code + the `ProxyHost.Create(...)` factory), `ClaudeCodeOllamaProxy.Console` (the `Microsoft.NET.Sdk.Web` console host, a one-line `Program.cs` that calls `ProxyHost`), and `ClaudeCodeOllamaProxy.UI` (a WinUI 3 unpackaged system-tray app that hosts `ProxyHost` **in-process**). Both hosts share `Core`.

```bash
# Build the whole solution
dotnet build

# Run the console host on the default Ollama port 11434 (uses Properties/launchSettings.json)
dotnet run --project ClaudeCodeOllamaProxy.Console

# Run on a different port — REQUIRED if a real Ollama already owns 11434.
# Note: --urls only wins with --no-launch-profile (the launch profile otherwise forces 11434).
dotnet run --project ClaudeCodeOllamaProxy.Console --no-launch-profile --urls "http://127.0.0.1:11435"

# Run the system-tray app (hosts the proxy in-process; port is set in its Settings tab, default 11434).
# Don't run this and the console host at the same time — they bind the same port.
dotnet run --project ClaudeCodeOllamaProxy.UI
```

There is **no test project**. Verification is done by smoke-testing endpoints against the real `claude` CLI (must be installed, on PATH, and authenticated via `claude login`). Examples are in `ClaudeCodeOllamaProxy.Console/ClaudeCodeOllamaProxy.http`. The two-step bridge test:

```bash
H=http://127.0.0.1:11435
# Discovery
curl -s $H/api/version          # -> {"version":"0.6.4"}
curl -s $H/api/tags
curl -s -X POST $H/api/show -H "Content-Type: application/json" -d '{"model":"sonnet"}'
# Ask (read-only, streamed SSE)
curl -sN -X POST $H/v1/chat/completions -H "Content-Type: application/json" \
  -d '{"model":"sonnet","stream":true,"messages":[{"role":"user","content":"say hi"}]}'
# Agent bridge: request 1 returns a tool_call (finish_reason "tool_calls"); a follow-up request
# containing a role:"tool" message with the same tool_call_id resumes the SAME parked session.
```

The listening URL prints to the console on startup. For the most-verbose logs (HTTP requests/responses incl. SSE chunks, the claude CLI command line, and CLI stdout/stderr), set the minimum level to `Trace` — `Logging__LogLevel__Default=Trace` is the single switch (Kestrel stays quiet because `Microsoft.AspNetCore` is pinned to `Warning`). **Do not** re-add per-category `Information` entries under `Logging:LogLevel` for `ClaudeCodeOllamaProxy*`/`Claude.AgentSdk` — a more-specific category rule overrides `Default`, which silently defeats the `Default=Trace` switch (the global category filter gates before any provider, including the file sink's `MinLevel`). The tray app exposes the same switch as the **Logging verbosity** picker on its Logs tab, applied **live** via `Service/Logging/MutableRuntimeConfigurationSource.cs` (an `IConfigurationSource` whose `Set(key, value)` calls `OnReload()`; `LoggerFactory` is change-token-bound to `IOptionsMonitor<LoggerFilterOptions>`, so the filter rules rebuild in place). `ProxyHostController` adds that source from `ProxyHost.Create`'s `configure` callback — cast to `IConfigurationBuilder` to reach `Add(IConfigurationSource)`, then re-call `builder.Logging.AddConfiguration(...)` because the source lands after `CreateBuilder` wired the `Logging` section — and it sets **only** `Logging:LogLevel:Default`, for the reason above.

## Architecture (the big picture)

Minimal-API server. **`ClaudeCodeOllamaProxy.Core/ProxyHost.cs`** (`ProxyHost.Create(args, configure?)`) wires DI singletons, file logging, snake_case JSON, the loopback `11434` default, warms the model catalog (on `ApplicationStarted`), and maps three endpoint groups — returning a configured `WebApplication`. Both hosts call it: `ClaudeCodeOllamaProxy.Console/Program.cs` is just `ProxyHost.Create(args).Run();`, and the WinUI app's `ProxyHostController` calls `ProxyHost.Create(["--urls", …], b => b.Logging.AddProvider(…))` then `StartAsync()`/`StopAsync()` to host it in-process. `Create` sets `ContentRootPath = AppContext.BaseDirectory` because `appsettings.json` ships as copied content of `Core` (it lands in each host's `bin`, and flows to the UI's output transitively). The `Logging:File` `TextBuilderType` is assembly-qualified to **`ClaudeCodeOllamaProxy.Core`**.

**The WinUI tray app (`ClaudeCodeOllamaProxy.UI`)** is a thin shell around `ProxyHost`, modeled on `H.NotifyIcon.Apps.WinUI`. It's **unpackaged** (`WindowsPackageType=None`) and **single-instance** (`Program.cs` uses `AppInstance.FindOrRegisterForKey` + activation redirection, with `DISABLE_XAML_GENERATED_MAIN` so redirection happens before `Application.Start`). `App` keeps a field reference to `TrayIconView` (so the `H.NotifyIcon` `TaskbarIcon` isn't GC'd) and hides-on-close (`HandleClosedEvents`); only the tray **Quit** truly exits. **Left-clicking the tray icon toggles** (`App.ToggleMainWindow`): minimize if the window is on screen *and* focused, otherwise show + foreground. Focus can't be read with a bare `GetForegroundWindow()` at click time — clicking the notification area activates the shell's taskbar first, so `MainWindow` tracks its own `Activated`/`Deactivated` and exposes `WasRecentlyActive` (active, or deactivated within 400 ms). "On screen" is Win32 `IsWindowVisible && !IsIconic`, because hide-to-tray is a raw `ShowWindow(SW_HIDE)` that XAML doesn't model. The tray menu's **Open** item is still a plain show, not a toggle. All four pages (**Home, Logs, Settings, About**) are in `NavigationView.MenuItems`, in that order — there is no `FooterMenuItems` block, and `IsSettingsVisible="False"` (Settings is a hand-rolled item). **Settings are placed next to what they affect, not all on the Settings page:** **Port** lives on Home beside the listening URL it controls (with the restart-needed `InfoBar`), **LogLevel** and **ClaudeCliDebug** live on Logs, and Settings holds the rest (theme, startup, tray, admin, update checking, window size) plus the global reset. `ProxyHostController` owns the in-process host and pipes its logs to the Logs page via an `ObservableLoggerProvider` (marshaled onto the UI thread by `DispatcherQueue`). **The Logs page renders that buffer into a single read-only `TextBox`, not a `ListView`** — text selection must be able to span lines, and a `ListView` can only select whole rows (worse, a per-row `IsTextSelectionEnabled` `TextBlock` swallows the pointer, so even row selection stops working). The trade-off is that the whole text is re-assigned on update, which drops any selection: `LogsPage` therefore coalesces renders on a 150 ms `DispatcherQueueTimer` and **defers a render while `SelectionLength > 0`** (re-running it when the selection clears), and only auto-scrolls when already at the bottom. **That provider is app-lifetime, not host-lifetime:** its `Dispose()` is deliberately a no-op, because the host disposes its providers on shutdown and nulling `LineLogged` there silenced the Logs page after the first stop/restart. User settings live in `SettingsStore` (`%LOCALAPPDATA%\ClaudeCodeOllamaProxy.UI\settings.json`): **Port** (the host binds `--urls http://127.0.0.1:{Port}`; captured at start, so it needs a restart), **Theme** (`System`/`Light`/`Dark`), and two settings pushed into the running host's configuration so they apply **live** — **LogLevel** (`ApplyLogLevel`, also sets the provider's `MinLevel`) and **ClaudeCliDebug** (`ApplyClaudeCliDebug` → `Claude:CliDebug`), plus **CheckForUpdatesOnStartup** (default **true**) and **IncludePrereleaseUpdates**. Both live-host settings are re-applied by the Settings page's "Reset to default settings", which otherwise wouldn't reach the host now that those controls live on another page (each page re-reads settings in `OnNavigatedTo`, so its controls catch up on next navigation). `StartupManager` toggles the `HKCU\…\Run` key (command includes `--startup`, which makes `App` start hidden in the tray). **Theme** (`ThemeHelper` + `App.ApplyTheme`): sets the window `RequestedTheme`; the tray icon is always `Assets/AppIcon.ico` (the brand-orange Claude Code glyph), the same in every theme. `System` follows the OS via `UISettings.ColorValuesChanged` + the `…\Themes\Personalize` registry value (used for the title-bar color via `TitleBarThemeHelper`). **Update checking** (`Services/AppVersion.cs`, `Services/UpdateChecker.cs`, `Views/UpdateDialog.cs`) is read-only: `UpdateChecker` asks the GitHub API (via **Octokit**, the UI project's only network dependency) for `icnocop/ClaudeCodeOllamaProxy` releases and compares the newest tag against the running assembly version. Nothing is downloaded or installed — the About page's **Check for updates** button and the startup check only raise a `ContentDialog` and an `InfoBar` that link to the release page. `GetAll` is used rather than `GetLatest` because `GetLatest` can't be told to honor **IncludePrereleaseUpdates**; drafts are invisible either way (they need an authenticated token), which matters because `build.yml` creates **draft** releases — one is only visible to the check after it's published by hand. `CheckAsync` deliberately **throws** on network/API failure so the caller can distinguish "up to date" from "couldn't check"; the About button shows the error, the startup check swallows it. Results are cached in `UpdateChecker.Known` and broadcast via the static `UpdateStateChanged` event, because the startup check can finish before *or* after the About page and `MainWindow` exist — both seed from `Known` and then subscribe (and unsubscribe in `OnNavigatedFrom` / `DetachStatusIcon`). The startup check shows its dialog **only when the window is on screen** (`WindowActivationHelper.IsOnScreen`), so starting hidden in the tray isn't defeated. The silent notice is carried by three surfaces: an icon `InfoBadge` on the About nav item (an icon badge, not the default 4px dot — that was too easy to miss), a line in the tray tooltip, and an **update marker composed into the tray/taskbar icon itself** — `StatusIconRenderer.CreateIcon`/`EnsureIconFile` take an `updateAvailable` flag and draw a blue disc with a white download arrow in the **top-left**, diagonally opposite the bottom-right `ProxyState` circle so the two never overlap or get confused (its hue is deliberately unused by any state). Below 24px the arrow's stem is dropped — at 16px it would smear into one gray pixel. `EnsureIconFile`'s per-run cache is therefore keyed on `(state, updateAvailable)`, and both `TrayIconView` and `MainWindow` recompose their icon on `UpdateStateChanged` as well as on `StateChanged`. **The version must be stamped by CI to mean anything:** `build.yml` computes both `NUMBER` (`2026.06.28.9`, passed as `-p:Version` to every `dotnet publish`) and `VERSION` (`v` + NUMBER, the tag/zip name) — keep them in lock-step. A build from source has no `<Version>`, reports `1.0.0.0`, and therefore always finds an update; that's intentional (`AppVersion.IsDevelopmentBuild`). `AppVersion.Display` prefers the informational version and trims the SDK's `+<sha>` suffix so About reads `2026.06.28.9`, matching the tag, rather than the normalized `Version` form `2026.6.28.9` used for comparison. The UI tests suppress the startup check with the `CLAUDECODEOLLAMAPROXY_UI_SKIP_UPDATE_CHECK` env var (set by `AppDriver`) rather than by turning the setting off — so screenshot runs stay off the network and can't catch the dialog in frame, while the Settings screenshot still shows the toggle in its shipped **on** state.

**Platforms:** the WinUI project builds for **x64/x86/ARM64 only (no Any CPU)**, so the `.slnx` declares those three solution platforms (the Any CPU `Core`/`Console` projects map automatically) and the UI has a `Properties/launchSettings.json` (`commandName: Project`) — without those, VS reports "the startup project cannot be launched" under an Any CPU solution platform.

**Two protocols, by design (verified against `microsoft/vscode-copilot-chat`):** Copilot's Ollama Bring Your Own Model provider does *discovery* over the native Ollama API but sends *chat* to the OpenAI `/v1/chat/completions` endpoint as SSE.

- `Endpoints/OllamaDiscoveryEndpoints.cs` — `/api/version` (must report ≥ 0.6.4), `/api/tags`, `/api/show`, `/v1/models`. **Load-bearing detail in `/api/show`:** emit both `model_info["general.architecture"]="claude"` and `model_info["claude.context_length"]=N` (Copilot builds that key dynamically and silently clamps context to 32768 if missing), and include `"tools"` in `capabilities` or Copilot disables Agent mode for the model.
- `Endpoints/OpenAiChatEndpoint.cs` — the chat entry point Copilot actually uses. Dispatches by mode.
- `Endpoints/OllamaChatEndpoint.cs` — native `/api/chat` NDJSON, **text-only** (no bridge); for non-Copilot clients and smoke tests.

**Mode is implicit.** `Services/ModeDetector.cs` infers Ask / Plan / Agent from the request's `tools` array (edit tools like `apply_patch`/`create_file` ⇒ Agent). There is no `mode` field and no permission knob in config — Ask/Plan map to Claude `PermissionMode.Plan` (read-only); Agent maps to `AcceptEdits` + the bridge.

**The tool-call bridge (`Bridge/`) is the core mechanism and the trickiest code.** Copilot's native diff/accept UI only works if the model returns `tool_calls` to Copilot's *own* edit tools (Copilot applies them via `WorkspaceEdit`). The Claude CLI instead uses its own tools, and the SDK's `canUseTool` callback cannot inject a synthetic result — so the bridge runs through **in-process MCP tools**:
- `CopilotToolServerBuilder` turns Copilot's `tools[]` into an `McpToolServer` (`mcp__copilot__<tool>`), passing each tool's JSON schema through verbatim. Claude's own mutating tools (Write/Edit/MultiEdit, and Bash when `BridgeTerminalTool`) are disallowed so edits *must* flow through the bridge; read-only built-ins stay enabled.
- `ToolBridge` holds one long-lived `ClaudeAgentSession`. A background pump reads `ReceiveResponseAsync` and pushes text/done events into a `Channel<BridgeEvent>`. When Claude calls a bridged tool, the MCP handler emits a `ToolCallEvent`, registers a `TaskCompletionSource` in `BridgeRegistry` keyed by `tool_call_id`, and **blocks indefinitely**. `DrainAsync` writes one HTTP response until it hits a tool call (emit `finish_reason:"tool_calls"`, end response, keep session parked) or completion (`stop`, dispose).
- A follow-up Copilot request carrying a `role:"tool"` result with a registered `tool_call_id` is a **continuation**: `BridgeRegistry.TryResolve` unblocks the handler, and `DrainAsync` resumes streaming the *same* session. Correlation is purely by `tool_call_id`; bridge state is in-memory only (a restart drops an active tool loop).
- **tool_call ids MUST be globally unique** — generated by `BridgeRegistry.NextCallId()` (a process-wide counter), never per-bridge. Per-bridge ids collide across concurrent bridges and cross-deliver results to the wrong session (a real bug that was fixed). **One bridge per conversation:** the endpoint keys bridges by the first user message (`ConversationKey`, deliberately not the system prompt — VS injects volatile dates there) and disposes any existing bridge for that conversation before starting a new turn, so a resend never runs two Claude sessions on the same workspace. Bridges are also disposed on client disconnect (HTTP 499) / errors via `DrainAndDisposeAsync`, so abandoned sessions don't linger.
- **Never pass large content as a CLI argument (Windows ~32 KB command-line limit).** Copilot's Agent-mode system prompt is tens of KB; passing it as `--system-prompt` (or a long conversation as `--print`) throws `Win32Exception (206): The filename or extension is too long`. So `BuildOptions` deliberately has **no system-prompt parameter**, all chat paths use a **bidirectional session** (prompt over stdin via `SendAsync`, never `--print`/`QueryAsync`), and `OpenAiMessageMapper.CombineSystemAndPrompt` folds the system prompt into the stdin prompt as an `<operator_instructions>` preamble (Claude Code keeps its own default system prompt). Keep it this way — reintroducing `SystemPrompt`/`--print` for big inputs re-breaks Agent mode.
- **MCP env tuning** (`ClaudeSessionFactory` → SDK `Environment`): `MCP_TOOL_TIMEOUT` (from `Claude.McpToolTimeoutMs`) and `MAX_MCP_OUTPUT_TOKENS` (from `Claude.MaxMcpOutputTokens`) — the latter prevents large `read_file`/search results from truncating at the ~10k-token default. Copilot's own per-tool caps (e.g. `debugger_launch_unit_test` ~30s) are VS-side and not controllable here.

**Claude CLI integration:**
- `Services/ClaudeSessionFactory.cs` is the single place that builds `ClaudeAgentOptions` and wires the SDK's `OnStderr`/`OnMessageSent`/`OnMessageReceived` to Trace logging. Auth flows through the CLI's own `claude login` (no ApiKey/BaseUrl option exists).
- `Services/ChatService.cs` handles the read-only (Ask/Plan) path. Like the bridge, it uses a bidirectional session (`SendAsync` over stdin), not `QueryAsync`/`--print`, so large prompts never become a CLI argument.
- `Services/ModelCatalog.cs` discovers the base model list from the CLI (cached with a TTL) and **expands each base model across its supported effort levels** into selectable variants (id `"<base>:<effort>"`, label `"Opus 4.8 (1M context) · high effort"`). **Primary source is the CLI's `initialize` control_response, not `supported_models`.** The init handshake (which always succeeds) returns a rich `models` array — `value` (the exact CLI model value, e.g. `opus[1m]`/`claude-fable-5[1m]`, used verbatim as both the base id and the `--model` arg), `displayName`/`description`, `supportsEffort`, and per-model `supportedEffortLevels`. The SDK discards that response, so the catalog captures it off the raw stdout stream via `OnMessageReceived` (fires for every line before parsing) during `CreateSessionAsync`, then parses `response.response.models[]` (skipping the `default` pseudo-alias). **Effort levels are per-model** (from `supportedEffortLevels`, intersected with the configured `SupportedEfforts` allow-list): Opus/Fable get low–max, Sonnet has no `xhigh`, and Haiku (no `supportsEffort`) surfaces as a **single no-effort variant** (id `haiku`, no `:effort` suffix, `ModelSelection.Effort == null` ⇒ no `--effort`). Context length and capabilities are **not** in the init payload, so they still come from the `ModelDefaults` table (matched by id substring — `opus[1m]` contains `opus` — with `"*"` fallback); friendly name prefers `ModelDefaults.DisplayName`, then the label parsed from the init `description`. `ResolveSelection(id)` parses the `:<effort>` suffix back into `(baseModel, effort)`; `ResolveAsync` builds the variant for `/api/show`. **The default model** (used when a request omits the model — `DefaultModelIdAsync`/`DefaultBaseAsync`) is the one the init payload marks with its `value:"default"` entry (`ResolveDefaultBaseId` matches it to a real model by description, e.g. Opus), falling back to the first discovered model. **Fallbacks:** if init parsing yields nothing, it retries the `supported_models` control request (older CLIs reject it); failing that, the `sonnet`/`opus`/`haiku`/`fable` aliases (expanded across all configured efforts, the legacy behavior). **Configured extra models:** `WithKnownModels` unions `Claude.KnownModels` (the nine currently-active Anthropic ids) into the discovered list after *whichever* tier produced it, so specific versions are pickable even when the CLI only reports family aliases. Dedupe is by id with any `[...]` variant suffix stripped (`NormalizeId`), so a CLI-reported `opus[1m]` suppresses a configured `opus` — the CLI's own value wins. These entries have no CLI payload, so their effort metadata comes from `ModelDefaults.SupportsEffort`/`SupportedEfforts` (CLI-reported models still use the init payload's `supportedEffortLevels`). Because VS uses the **label** as the model identifier, alias `DisplayName`s are deliberately version-neutral (`"Opus"`, not `"Opus 4.8"`) so they can't collide with the explicit-version rows. **Ordering:** `GetModelsAsync` sorts by friendly name (ordinal-ignore-case, `ThenBy` id) and `EffortsFor` orders by the `ValidEfforts` index, so the picker reads `Opus ×5, Opus 4.6 ×5, Opus 4.7 ×5, Opus 4.8 ×5, Opus 5 ×5, …` with efforts lightest→heaviest. The sort is applied on the way out, **not** to `_baseCache` — `DefaultBaseAsync`'s "first discovered model" fallback still means first *discovered*, not first alphabetically.
- **Effort:** the AJGit SDK has no effort option, so `ClaudeSessionFactory.BuildOptions(effort:)` passes `--effort <level>` to the CLI via `ExtraArgs` (alongside `--debug` when `Claude.CliDebug` is set — **not** inferred from the log level; that coupling was removed so raising verbosity to Trace can't silently enable CLI debug output. `ClaudeSessionFactory` takes `IOptionsMonitor<ProxyOptions>` and reads `CurrentValue` per session, so the toggle applies to the next request without a host restart). Valid flag values are `low|medium|high|xhigh|max` only (the CLI warns-and-defaults on unknown values; `ultracode`/`auto` are interactive-`/effort`-only). Copilot has no effort UI, so effort is selected by picking a model variant; chat endpoints resolve the id via `ResolveSelectionAsync`, run the CLI with the **base model** + `--effort`, and echo the requested id back to the client.
- **VS 2026 Copilot uses the `/api/tags` `name` field as the model identifier** (not `model`, contrary to the VS Code source) — it sends the friendly label (`Opus 5 (1M context) · high effort`) back as the chat `model`. So `name` carries the friendly `DisplayLabel`, and **labels must be unique across the catalog** (see the version-neutral alias names above). `ModelCatalog.ResolveSelectionAsync`/`ResolveAsync` match the catalog by **both** the clean id (`claude-opus-5:high`) and the display label, then map to the base model. **Never pass the requested id straight to `--model`** — always resolve it first, or the CLI gets an invalid model name and exits 1 (the original Agent-mode failure). **The picker renders each row as `{name} ({family}, {format}) ({name})` — VS repeats `name` (as title and as id-in-parens) and ignores both `model` and the `/api/show` `display_name`, so the label unavoidably appears twice; there is no proxy-side way to show a separate friendly title + id.** (`family`/`format` = `OllamaModelDetails` defaults `claude`/`api`.)
- `Services/OpenAiMessageMapper.cs` flattens OpenAI messages (incl. multi-part content) into a Claude prompt; `Services/ImageMaterializer.cs` writes image parts to temp files referenced by path (the SDK has no native image input); `Services/WorkingDirectoryResolver.cs` infers the solution directory from absolute paths in the request (Copilot does not pass the workspace path) with an `appsettings.json` override.

## Gotchas

- **The model list is still CLI-driven — don't hardcode one in code.** `appsettings.json` holds capability/context defaults (`ModelDefaults`) plus `Claude.KnownModels`, a *supplementary* list of ids unioned onto whatever the CLI reports so specific Anthropic versions are pickable. Discovery remains the source of truth: known entries never replace a CLI-reported model (dedupe strips `[...]` variant suffixes so `opus[1m]` wins over `opus`), and the list is config, not a C# constant.
- **`.NET config binding APPENDS to non-empty `List<T>` initializers.** `ModelCapabilities.Capabilities` and `ModelCapabilities.SupportedEfforts` are intentionally initialized empty to avoid duplicate entries; keep them that way. (Re-binding on config reload is safe — `IOptionsMonitor` binds a fresh instance each time, so live settings changes don't accumulate list items.)
- The SDK's published `0.6.1` API matches its `main`-branch source; namespaces split across `Claude.AgentSdk` (client/options/`PermissionMode`/`McpSdkServerConfig`), `Claude.AgentSdk.Messages`, `Claude.AgentSdk.Tools` (`SdkMcpTool`/`McpToolServer`/`ToolResult`), `Claude.AgentSdk.Protocol`, and `Claude.AgentSdk.Exceptions` (`CliNotFoundException`).
- File logging (`Service/Logging/`, namespace `ClaudeCodeOllamaProxy.Service.Logging`) uses `Karambolo.Extensions.Logging.File`, which has **no native `MaxFiles`** (a startup sweep in `LaunchPlaceholderResolver` keeps newest 3) and no `<appname>`/`<launch>` placeholders (provided by `LaunchPlaceholderResolver.Resolve`, assigned to Karambolo's `PathPlaceholderResolver` option). The `Logging:File` section must be nested under `Logging`, and per-file level uses `MinLevel`.
- **The proxy bridges exactly the tools Copilot sends, and cannot add ones it doesn't.** Each VS Copilot mode (Ask/Plan/Agent, and the Debugger/Modernize/Profiler/Test variants) ships a fixed tool set chosen by Copilot. So in Debugger mode Claude only sees what Copilot provides — e.g. launch test, set breakpoints, read the output window, but **no** `debugger_continue`/`debugger_evaluate_expression`. If Claude reports a missing debugger tool, that's Copilot's tool set for that mode, not a proxy bug — there is no proxy-side fix.
